# معماری احراز هویت، نشست و جداسازی کاربران

## دو مفهوم که نباید قاطی شوند

BilitFast با **دو نشست کاملاً جدا** کار می‌کند و خلط آن‌ها منشأ بیشتر
سوءتفاهم‌هاست:

| | نشست BilitFast | نشست صفیر ریل |
|---|---|---|
| چیست | حساب کاربر در خود برنامه | کوکی ورود به سایت صفیر ریل |
| شکل | توکن امضاشده (HMAC) | `PHPSESSID`، `cookname`، `cookid` |
| کجا | `Authorization: Bearer` | رکورد کاربر در دیتابیس (رمزشده) |
| خروج | باطل می‌شود | **دست نمی‌خورد** |

خروج از حساب BilitFast عمداً کوکی صفیر ریل را پاک نمی‌کند. آن کوکی حاصل
زحمت کاربر برای اتصال مرورگر است و پاک کردنش یعنی شروع دوباره از صفر.

---

## لایه‌ها

```
lib/auth.js       ← احراز هویت: هش گذرواژه، امضا و بررسی توکن
lib/accounts.js   ← مجوز: نقش، فعال/غیرفعال، انقضا، سهمیه، ابطال نشست
lib/apiauth.js    ← نگهبان API: کنار هم گذاشتن دو لایه بالا
```

`lib/auth.js` عمداً دست‌نخورده ماند. کاری که می‌کرد درست بود و چند جای پروژه
به آن وابسته‌اند؛ چیزی که اضافه شد مفاهیم *مجوز* است نه *احراز هویت*.

### هش گذرواژه

`scrypt` با پارامترهای `N=16384, r=8, p=1` و نمک تصادفی ۱۶ بایتی، مقایسه با
`timingSafeEqual`. از bcrypt/argon2 استفاده نشد چون `scrypt` در خود Node
هست و افزودن وابستگی بومی، ساخت Docker و نسخه دسکتاپ را شکننده می‌کند.
`scrypt` در برابر سخت‌افزار اختصاصی مقاوم است و برای این کاربرد کافی.

### توکن نشست

```
base64url({type, uid, iat, exp}) + "." + HMAC-SHA256(body, SESSION_KEY)
```

بدون حالت (stateless)، عمر ۷ روز. کلید از `lib/secrets.js` می‌آید و در تولید
اگر تنظیم نشده باشد سرویس بالا نمی‌آید.

### خروج واقعی

توکن بدون‌حالت را نمی‌شود «پاک» کرد. راه‌حل: مُهر زمانی `sessions_revoked_at`
روی رکورد کاربر. هر توکنی که `iat` آن از این مُهر قدیمی‌تر باشد رد می‌شود.

مقایسه **اکیداً بزرگ‌تر** است نه بزرگ‌تر-یا-مساوی: چون هر دو با دقت
میلی‌ثانیه ثبت می‌شوند، توکن صادرشده در همان میلی‌ثانیهٔ خروج مبهم است و
حالت مبهم باید رد شود. بدترین پیامد این سخت‌گیری یک بار ورود دوباره است؛
بدترین پیامد سهل‌گیری، زنده ماندن توکنی است که کاربر فکر می‌کند بسته شده.

ابطال نشست در این موارد هم اتفاق می‌افتد: غیرفعال شدن حساب، و تغییر گذرواژه
توسط مدیر.

## مدل کاربر

```js
{
  id, username, pass: { salt, hash, alg: 'scrypt' },
  display_name, role,              // 'admin' | 'tester' | 'user'
  is_active, expires_at,
  max_searches, max_reservations,  // null = نامحدود
  usage: { searches, reservations },
  sessions_revoked_at,
  safir_credentials,               // رمزشده با AES-256-GCM
  safir_cookies, safir_cookies_at,
  created_at, updated_at
}
```

### سازگاری با داده موجود

کاربران فعلی هیچ‌کدام از فیلدهای جدید را ندارند. **هیچ migration ای اجرا
نمی‌شود.** `normalizeUser()` هنگام خواندن مقادیر پیش‌فرضِ امن می‌گذارد:

| فیلد نبود | پیش‌فرض |
|---|---|
| `role` | `'user'` |
| `is_active` | `true` |
| `expires_at` | `null` (بدون انقضا) |
| `max_searches` / `max_reservations` | `null` (نامحدود) |

یعنی حساب‌های موجود دقیقاً مثل قبل کار می‌کنند و رکوردشان تا نخستین ویرایش
دست‌نخورده می‌ماند.

## حالت تک‌کاربره در برابر چندکاربره

اجبار ورود با `BILITFAST_MULTIUSER` کنترل می‌شود:

| مقدار | رفتار |
|---|---|
| `1` | ورود همیشه اجباری (سرور، Docker، `server.js`) |
| `0` | ورود هرگز اجباری نیست (تک‌کاربره صریح) |
| تنظیم‌نشده | اگر حتی یک کاربر ثبت شده باشد → اجباری |

منطق پیش‌فرض عمدی است: کسی که برنامه را روی لپ‌تاپ خودش اجرا می‌کند نباید
مجبور به ساخت حساب شود، ولی به محض اینکه چند حساب وجود داشت، «بدون ورود هم
کار می‌کند» تبدیل به حفره می‌شود.

روی `server.js` این متغیر به‌صورت خودکار `1` می‌شود.

## جداسازی نشست صفیر ریل

```
کاربر A ──► safir_credentials (رمزشده) ──► نشست صفیر A
کاربر B ──► safir_credentials (رمزشده) ──► نشست صفیر B
```

هر کوکی روی رکورد همان کاربر ذخیره می‌شود. سه نقطه‌ای که جداسازی در آن‌ها
اعمال می‌شود:

1. **`lib/session-fallback.js`** — وقتی کلاینت کوکی نمی‌فرستد، سرور تلاش
   می‌کند نشست بسازد. این تابع حالا کاربر را می‌گیرد و فقط از اعتبارنامه
   *خودِ همان کاربر* بازیابی می‌کند.

   > این یک باگ واقعی بود: پیش از این همیشه سراغ اعتبارنامه محلیِ سراسری
   > می‌رفت، یعنی روی نصب چندکاربره کاربری که کوکی نفرستاده بود می‌توانست
   > با نشست صفیرِ شخص دیگری جستجو یا رزرو کند. مسیر محلی حالا فقط وقتی
   > مجاز است که هیچ کاربری در کار نباشد.

2. **`api/cookie-sync.js`** — کد جفت‌سازی افزونه با `owner` برچسب می‌خورد
   (`u:<id>` یا `local`) و فقط همان مالک می‌تواند تحویلش بگیرد.

3. **`api/safir-session.js`** — همه اقدام‌ها روی `user.id` نشست جاری.

`bookings` و `server_monitors` از قبل با `user_id` فیلتر می‌شدند.

## کنترل دسترسی

| نقش | دسترسی |
|---|---|
| `admin` | مدیریت کاربران، گزارش فعالیت، همه امکانات |
| `tester` | امکانات عادی، معمولاً با انقضا و سهمیه |
| `user` | امکانات عادی |

`requireAdmin()` روی خطای دسترسی پیام عمومی «شما به این بخش دسترسی ندارید»
می‌دهد و وجود یا نبود منبع را لو نمی‌دهد.

دو محافظ در برابر قفل شدن سیستم: آخرین ادمین فعال را نه می‌شود از نقش
انداخت، نه غیرفعال کرد، نه حذف کرد؛ و کاربر نمی‌تواند حساب خودش را حذف کند.

## سهمیه

```js
accounts.quotaStatus(user, 'searches')      // بررسی بدون مصرف
accounts.consumeQuota(userId, 'searches')   // مصرف + نوشتن
```

سهمیه **پیش از** تماس با صفیر ریل مصرف می‌شود. اگر بعد از آن مصرف می‌شد،
چند درخواست موازی می‌توانستند هم‌زمان از سد بگذرند.

سهمیه رزرو فقط در گام `start` مصرف می‌شود نه `submit`، وگرنه هر تلاش دوباره
روی کپچا یک واحد از سهمیه کاربر را می‌خورد.

پاسخ عبور از سهمیه: `429` با `quotaExceeded: true`.

## محافظت از ورود

دو لایه:

1. **بر اساس آی‌پی** (`guardApi`) — ۱۰ درخواست در دقیقه روی `login`.
2. **بر اساس نام کاربری** (`isLockedOut`) — ۸ تلاش ناموفق در ۱۵ دقیقه →
   قفل ۱۰ دقیقه‌ای.

لایه دوم لازم است چون مهاجم با botnet از صدها آی‌پی همان یک حساب را هدف
می‌گیرد و لایه اول را بی‌اثر می‌کند.

قفل عمداً **موقت** است. اگر حساب را دائمی می‌بستیم، مهاجم می‌توانست با تلاش
عمدی ناموفق کاربر واقعی را برای همیشه بیرون نگه دارد.

## گزارش فعالیت

`lib/activity.js` رویدادها را ثبت می‌کند: `LOGIN`، `LOGIN_FAILED`،
`LOGIN_BLOCKED`، `LOGOUT`، `USER_CREATED`، `USER_UPDATED`، `USER_DELETED`،
`PASSWORD_RESET`، `ADMIN_BOOTSTRAP`.

**ماژول خودش ورودی را پالایش می‌کند** و به فراخوان‌ها اعتماد نمی‌کند: هر
کلیدی که با `pass|password|secret|token|cookie|credential|authorization|apikey|otp|pin`
بخواند با `[حذف‌شده]` جایگزین می‌شود، و هر مقداری که شبیه کوکی صفیر باشد
(`PHPSESSID=`، `cookname=`، `cookid=`) هم همین‌طور. یک لاگِ نشت‌دهنده بدتر
از نبودِ لاگ است.

برای عیب‌یابی کوکی فقط فراداده بی‌خطر ثبت می‌شود:

```js
activity.cookieMeta(cookies)
// { cookieCount: 3, cookieNames: ['PHPSESSID','cookname'], hasSessionCookie: true }
```

لاگ روی `MAX_EVENTS = 5000` هرس می‌شود تا `db.json` بی‌مهار رشد نکند.

## APIها

| مسیر | دسترسی |
|---|---|
| `POST /api/auth` (`login`/`register`/`bootstrap`) | آزاد |
| `POST /api/auth` (`me`/`logout`/`change-password`) | نشست معتبر |
| `POST /api/admin-users` (`bootstrap`) | فقط وقتی هیچ ادمینی نیست |
| `POST /api/admin-users` (بقیه) | فقط `admin` |
| `POST /api/search` | ورود (در حالت چندکاربره) + سهمیه |
| `POST /api/reserve` | ورود (در حالت چندکاربره) + سهمیه |
| `POST /api/safir-session` | نشست معتبر |
| `POST /api/bookings` | نشست معتبر، فیلتر با `user_id` |
| `GET /api/health`, `/api/cities`, `/api/config` | آزاد (بدون داده کاربر) |

کدهای پاسخ:

| کد | معنی |
|---|---|
| `401` | وارد نشده‌اید یا نشست باطل شده |
| `403` | حساب غیرفعال/منقضی، یا دسترسی نقش کافی نیست |
| `429` | عبور از محدودیت نرخ، قفل ورود، یا اتمام سهمیه |
| `402` | مجوز/دوره آزمایشی برنامه تمام شده |
