# امنیت — راهنمای استقرار و پاسخ به ممیزی

این سند وضعیت هر یافته ممیزی امنیتی و کاری که انجام شده را ثبت می‌کند.
تست‌های رگرسیون در `test/security-audit.test.js` هستند: `npm run audit:security`

---

## متغیرهای محیطی اجباری در تولید

بدون این‌ها سرویس در حالت تولید **بالا نمی‌آید** (fail-closed):

```bash
# ساخت هر کلید:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

BILITFAST_SESSION_KEY=<64 hex>   # امضای نشست کاربران (جدا از بقیه)
BILITFAST_LICENSE_KEY=<64 hex>   # توکن مجوز/دوره آزمایشی
BILITFAST_TOKEN_KEY=<64 hex>     # رمزنگاری توکن وضعیت رزرو
```

یا فقط یک کلید ریشه بدهید؛ بقیه با HKDF از آن **مشتق و از هم جدا** می‌شوند:

```bash
BILITFAST_MASTER_KEY=<رشته تصادفی بلند>
```

اختیاری:

```bash
BILITFAST_INSTALL_KEY=<...>      # امضای نشانه نصب نسخه دسکتاپ
BILITFAST_CRON_SECRET=<...>      # فعال‌سازی پایش سرورلس با Cron
KV_REST_API_URL=/KV_REST_API_TOKEN=   # ذخیره‌ساز مشترک (Vercel KV)
UPSTASH_REDIS_REST_URL=/UPSTASH_REDIS_REST_TOKEN=  # یا Upstash
BILITFAST_ENFORCE_SECURITY=1     # اجبار حالت سخت‌گیرانه بدون NODE_ENV
```

> در **توسعه محلی** نیازی به تنظیم نیست: کلیدها هر بار اجرا به‌صورت تصادفی
> ساخته می‌شوند (نه ثابتِ قابل حدس). عارضه‌اش این است که با ری‌استارت،
> نشست‌های باز باطل می‌شوند — که رفتار درست و امن است.

## وضعیت یافته‌ها

### ۱. کلید پیش‌فرض قابل حدس برای نشست — ✅ رفع شد

**بود:** `process.env.BILITFAST_LICENSE_KEY || 'bilitfast-license-dev-only-key'`
چون این رشته در سورس عمومی است، هر کسی می‌توانست توکن نشست جعل و به حساب
دیگران وارد شود. ضمناً کلید نشست و کلید لایسنس یکی بودند.

**شد:** ماژول جدید `lib/secrets.js`:
- در تولید، نبود کلید = **توقف سرویس** (مثل `lib/token.js`).
- کلیدها **از هم جدا**: session / license / state / install.
- پشتیبانی از `BILITFAST_MASTER_KEY` با مشتق‌سازی HKDF (جداسازی دامنه).
- در توسعه، کلید **تصادفی هر اجرا** به‌جای ثابت قابل حدس.
- `dev-server.js` هنگام بالا آمدن `assertSecureConfig()` را اجرا می‌کند.

تست: جعل نشست با کلید پیش‌فرض قدیمی اکنون **رد** می‌شود.

### ۲. API انتقال کوکی بدون احراز هویت — ✅ رفع شد

**بود:** `push` و `poll` عمومی بودند؛ روی دامنه عمومی هر کسی با یک `poll`
آخرین `PHPSESSID` را می‌گرفت (ربودن نشست) یا با `push` کوکی خودش را جای
کوکی قربانی می‌نشاند.

**شد:** جریان **کد جفت‌سازی یک‌بارمصرف**:
1. برنامه `pair` می‌زند → کد ۶ رقمی (۲ دقیقه اعتبار) + `nonce` مخفی.
2. افزونه با `push` + همان کد کوکی می‌فرستد؛ **بدون کد معتبر رد می‌شود**.
3. `poll` فقط با `nonce` (که هرگز منتشر نمی‌شود) کوکی می‌دهد؛ سرور فقط
   **هشِ** nonce را نگه می‌دارد.
4. رکورد **بلافاصله پس از یک بار تحویل حذف** می‌شود؛ بازپخش ممکن نیست.
5. مالکیت رکورد به user/session گره خورده است.
6. روی دسترسی غیرمحلی، **ورود به حساب اجباری** است.

افزونه به نسخه ۱.۱ به‌روزرسانی شد (پنجره ورود کد به‌جای کلیک بی‌قید).

### ۳. کوکی و اطلاعات هویتی در localStorage — ✅ رفع شد

**شد:**
- **کوکی نشست** دیگر در `localStorage` نیست → `sessionStorage` (با بستن
  مرورگر پاک می‌شود). منبع پایدارش حساب کاربر روی سرور است.
- **داده هویتی** (کد ملی، تاریخ تولد، نام، موبایل در مسیرها و الگوهای
  مسافر) با **AES-256-GCM** رمز می‌شود (`public/secure-store.js`). کلید یک
  `CryptoKey` **غیرقابل‌استخراج** در IndexedDB است — با دسترسی به دیسک هم
  بیرون کشیدنی نیست.
- **کوچ خودکار** داده‌های متن‌سادهٔ نسخه‌های قبلی، بی‌صدا و یک‌باره.
- صفحه **`privacy.html`**: جدول شفاف داده‌ها + دکمه «حذف کامل داده‌های این
  دستگاه» + نمایش وضعیت امنیتی نصب.

> صادقانه: در برابر **XSS فعال** هیچ ذخیره‌سازی مرورگری کاملاً امن نیست
> (مهاجم از همان API استفاده می‌کند). این لایه ریسک دیسک/پشتیبان/پروفایل
> مشترک/افزونه خواننده را حذف می‌کند. CSP سخت‌گیرانه در `vercel.json` فعال است.

### ۴. ذخیره‌سازی JSON برای production — ✅ رفع شد

**شد:** `lib/db-remote.js` — درایور **Redis/Upstash یا Vercel KV** با همان
رابط. فعال‌سازی فقط با متغیر محیطی، بدون تغییر کد فراخوان (write-through +
کش با تازه‌سازی دوره‌ای).

`db.storageStatus()` وضعیت را گزارش می‌کند و `db.assertReliableStorage()`
در تولیدِ سرورلسِ بدون KV **جلوی بالا آمدن را می‌گیرد** تا داده بی‌صدا گم نشود.

| حالت | نتیجه |
|---|---|
| محلی/VM با فایل | `local-file` — پایدار ✅ |
| سرورلس + KV/Upstash | `shared-kv` — پایدار ✅ |
| سرورلس بدون KV | `ephemeral-tmp` — **هشدار/توقف** ⚠️ |

### ۵. پایش سمت سرور با serverless سازگار نیست — ✅ رفع شد

**شد:**
- `monitor.capability()` وضعیت را **صادقانه** گزارش می‌کند؛ روی سرورلسِ
  بدون Cron، اکشن `start` با خطای روشن **رد** می‌شود (به‌جای وعده دروغ).
- `resumeAll()` روی سرورلس اصلاً تایمر نمی‌سازد.
- `monitor.runDueMonitors()` + نقطه ورود **`api/cron.js`** برای Cron Job
  واقعی؛ `vercel.json` شامل `crons` هر دقیقه.
- امنیت Cron: `BILITFAST_CRON_SECRET` با مقایسه زمان‌ثابت (یا هدر رسمی
  `x-vercel-cron`).

### ۶. آسیب‌پذیری وابستگی jimp/file-type — ✅ کاهش‌یافته (mitigated)

**تحلیل:** آسیب‌پذیری (GHSA-5v7r-6r5c-r473) در **پارسر ASF** بستهٔ
`file-type` است که از طریق `@jimp/core` می‌آید: ورودی خراب می‌تواند حلقه
بی‌نهایت بسازد.

**چرا `npm audit fix --force` اجرا نشد:** نسخه امن `file-type@21.3.1`
**ESM-only** است و `@jimp/core@0.22` (CommonJS) به `^16.5.4` قفل است؛ مسیر
رسمی یعنی `jimp@1.6.1` که **بازنویسی کامل API** است و ۹ فایل از جمله کل
زنجیره OCR (`lib/captcha.js`, `lib/charlearn.js`, `lib/imageops.js`,
`lib/ocr/engine.js`) را می‌شکند. ارتقای عجولانه یعنی خرابی حل کپچا.

**مهار انجام‌شده:** `lib/image-guard.js` — هر بافری **قبل از رسیدن به Jimp**
با **امضای بایتی** بررسی می‌شود:
- فقط PNG / JPEG / GIF / BMP پذیرفته می‌شود؛
- **ASF/WMV و هر قالب دیگر رد می‌شود** ⇒ کد آسیب‌پذیر هرگز اجرا نمی‌شود؛
- سقف ۸ مگابایت و حداقل اندازه (منع مصرف حافظه و ورودی بریده).

اعمال‌شده روی هر دو مسیر ورودی تصویر: دریافت کپچا (`lib/reserve.js`) و
آپلود نمونه (`api/learn.js`).

> **کار آینده:** مهاجرت برنامه‌ریزی‌شده به `jimp@1.x` همراه با اجرای کامل
> `npm run test:ocr` و `npm run benchmark` پیش از ادغام.

### ۷. ناسازگاری نسخه undici — ✅ رفع شد

**بود:** `undici@8.10.2` نیازمند Node ≥ 22.19.0 بود ولی `package.json`
می‌گفت `>=18` → هشدار `EBADENGINE`.

**شد:** پین به `undici@^6.21.3` (نیازمند Node ≥ 18.17) و
`engines.node` به `>=18.17` اصلاح شد. اکنون `npm install` **بدون
EBADENGINE** است و لایه شبکه سریع روی Node 18/20/22 کار می‌کند.

## چک‌لیست استقرار تولید

```bash
# ۱) کلیدها
export BILITFAST_SESSION_KEY=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")
export BILITFAST_LICENSE_KEY=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")
export BILITFAST_TOKEN_KEY=$(node -e "console.log(require('crypto').randomBytes(32).toString('hex'))")

# ۲) ذخیره‌ساز مشترک (فقط اگر سرورلس/چندنمونه‌ای است)
export KV_REST_API_URL=...
export KV_REST_API_TOKEN=...

# ۳) پایش سرورلس (اختیاری)
export BILITFAST_CRON_SECRET=$(node -e "console.log(require('crypto').randomBytes(24).toString('hex'))")

# ۴) تست
npm test
npm run audit:security
```

**توصیه:** برای این محصول، اجرای روی **کامپیوتر کاربر یا VM ایران** بهترین
گزینه است — هم IP ایرانی برای صفیر، هم ذخیره‌سازی پایدار، هم پایش تایمری
قابل اتکا، بدون نیاز به KV و Cron.
