# تفکیک نتیجه جستجو و خطا در BilitFast 3.12.1

## علت مشکل
در 3.12.0 هر `!data.ok` بدون بررسی نوع خطا به افزایش شمارنده و تأخیر ۵ تا ۶۰ ثانیه می‌رفت. پاسخ سالم بدون ظرفیت (`ok:true, trains:[]`) درست پردازش می‌شد؛ اما پاسخ غیرعادیِ سامانه، مشکل نشست یا پاسخ خاص کپچا به شکل مناسبی جدا نشده بود.

## سیاست جدید

| نتیجه | جستجو | فاصله بعدی |
|---|---|---|
| `ok:true`، حداقل یک قطار | یافت شد | توقف پس از یافتن قطار |
| `ok:true`، `trains:[]` | پاسخ معتبر، ظرفیت پیدا نشد | فاصله عادی؛ شمارنده خطا صفر |
| `noCapacity:true` یا `NO_CAPACITY` | بدون ظرفیت | فاصله عادی؛ شمارنده خطا صفر |
| `captchaRequired` / `captchaInvalid` | اقدام انسانی لازم | توقف با راهنمایی؛ بدون بازآزمایی خودکار کپچا |
| `sessionInvalid` / `loginRequired` | نشست معتبر نیست | توقف با راهنمای ورود مجدد |
| HTTP 400/401/402/403/422، ورودی نامعتبر یا خطای دائمی | نیازمند اصلاح یا مجوز | توقف؛ بدون تأخیر فزاینده |
| قطع شبکه، HTTP 408/429/5xx مشخص، timeout | خطای ارتباطی | ۵، ۱۰، ۲۰، ۴۰، ۶۰ ثانیه؛ حداکثر ۱۵ بار پیاپی |
| پاسخ نامشخص | نتیجه قابل اعتماد نیست | توقف و نمایش پیام؛ نه تبدیل به ظرفیت صفر |

فاصله پایه در تنظیمات جاری ۲ ثانیه است؛ فاصله واقعی تحت‌تأثیر مدت پاسخ، تعداد مسیرهای فعال و محدودسازی درخواست‌هاست. تعداد درخواست‌ها نامحدود نیست اگر سقف سهمیه یا محدودیت خدمات اعمال شود.

### محدوده تغییر
این تغییر فقط دسته‌بندی پاسخ جستجو و سیاست Retry را اصلاح می‌کند؛ کپچا را حل نمی‌کند، توکن تولید نمی‌کند و محدودسازی واقعی سایت را دور نمی‌زند. نشانه `captchaRequired` تنها مانع ادامه خودکار می‌شود. تست‌های این نسخه با پاسخ‌های مصنوعی هستند، نه اتصال واقعی به سامانه.
