# BilitFast Web 3.13.1 — گزارش اصلاحات و دستور تحویل

**مبنا:** سورس کامل 3.13.0 ارسالی. این یک اصلاح مرحله‌ای است؛ ساختار اپلیکیشن، صفحات و افزونه حفظ شده‌اند.

## موارد اصلاح‌شده

1. **شکست CI** — اسکریپت‌های `audit:security` و `test:enterprise` در `package.json` تعریف و تست‌های معنادار به آن‌ها متصل شدند. workflow فعلی Linux/Windows همچنان همین دو دستور را اجرا می‌کند.
2. **پاسخ HTTP 200 جعلی** — `lib/core.js` اکنون پیش از برچسب «عدم ظرفیت» بازگشت به فرم ورود/URL ورود، صفحه کپچا، انتقال به دامنه دیگر، صفحه مسدود/ناشناخته و ساختار جدول یا پیام صریح نبود موجودی را بررسی می‌کند. برای پاسخ نامعلوم `ok:false` برمی‌گرداند تا حلقه جستجو بدون اخطار ادامه پیدا نکند.
3. **انتخاب قطار اشتباه** — `public/route.html` دیگر در نبود شماره قطار تعیین‌شده از اولین نتیجه استفاده نمی‌کند؛ تنها یک تطابق قطعی و دارای شناسه سرویس می‌تواند به رزرو خودکار برسد. ارقام فارسی/عربی در مقایسه شماره قطار یکسان‌سازی می‌شوند.
4. **تک‌سیستمی بودن نصب** — `lib/host-machine.js` اثر انگشت سیستم میزبان را از هویت سیستم‌عامل تولید می‌کند، `installation.json` تازه قالب v2 دارد و با جابه‌جایی فایل روی میزبان متفاوت، برنامه دسترسی را رد می‌کند. در Linux Docker فایل `/etc/machine-id` فقط برای خواندن از میزبان mount می‌شود. فایل v1 بدون مهاجرت با **کد اختصاصی امضاشده فروشنده** برای شناسه نصب و هش میزبان قابل استفاده نیست؛ تغییر متغیر محیطی به‌تنهایی کافی نیست.
5. **امنیت جفت‌کلید فروشنده** — `license-admin.js init` دیگر در نبود کلید خصوصی سابق، به‌صورت ناخواسته جفت‌کلید جدید تولید نمی‌کند. ایجاد اولین کلید فروشنده عملیاتی جداگانه و نیازمند اجازه صریح است. فایل `config/license-public.pem` **در سورس اولیه نبود** و عمداً با کلید دیگری جایگزین نشده است.
6. **هماهنگی نسخه** — `package.json`، `package-lock.json` و `extension/manifest.json` روی `3.13.1` هماهنگ شده‌اند؛ توضیح منسوخ «همان تب» در README از رفتار نسخه فعلی «تب جدید» متمایز شده است.
7. **تست‌های جدید** — سناریوهای URL ورود، فرم ورود، کپچا، نتیجه خالی، ردیف قطار با ظرفیت، پاسخ نامشخص، خطای HTTP، کپی نصب و مهاجرت قدیمی، کنترل هویت فروشنده و بررسی آماده‌بودن کلید عمومی اضافه شدند.

## دستورات کنترل کد

از پوشه `BilitFast-Web-SelfHosted`:

```bash
npm ci
npm test
npm run audit:security
npm run test:enterprise
```

توجه: این تست‌ها شبیه‌سازی و بررسی کد هستند، نه تأیید پذیرش رزرو توسط صفیرریل. تست‌های قدیمی `npm test` در محیط ممیزی با اتکا به mock اجرا شدند؛ `npm ci` تمیز به‌علت محدودیت محیط ممیزی قابل تأیید نبود. اجرای موفق npm ci و Docker build در محیط CI یا رایانه/سرور نهایی ضروری است.

## آماده‌سازی لایسنس در رایانه فروشنده

1. کلید خصوصی Ed25519 **موجود** فروشنده را در مسیر پیشین خودش (`~/.bilitfast-seller/vendor-private.pem` یا مسیر تنظیم‌شده با `BILITFAST_VENDOR_PRIVATE_KEY_PATH`) حفظ یا از پشتیبان **اصلی** بازیابی کنید.
2. `node scripts/license-admin.js init` را اجرا کنید تا `config/license-public.pem` از همان کلید خصوصی بازیابی و با آن تطبیق داده شود.
3. در **کپی staging بدون فایل .env و داده مشتری** دستور `npm run check:delivery` را اجرا کنید. بدون کلید عمومی، این کنترل عمداً با خطا پایان می‌یابد.
4. فقط `config/license-public.pem` را در سورس تحویلی بگذارید؛ هرگز فایل `vendor-private.pem` و کلیدهای `.env` را داخل ZIP مشتری نگذارید.
5. برای فروشنده‌ای که **تا کنون هیچ لایسنسی صادر نکرده است**، تنها در صورت قصد ایجاد هویت فروشنده جدید دستور `BILITFAST_ALLOW_NEW_VENDOR_KEY=1 node scripts/license-admin.js init-new` قابل اجرا است. اجرای آن برای فروشنده دارای کلید قدیمی توصیه نمی‌شود.

## نصب جدید روی Linux Server

نیازمند Docker Compose، یک دامنه معتبر با DNS روی همان سرور و HTTP/HTTPS قابل دسترس:

```bash
node scripts/setup-selfhost.js agency.example.com
docker compose -f compose.selfhost.yml up -d --build
docker compose -f compose.selfhost.yml ps
```

`compose.selfhost.yml` از مسیر میزبان `/etc/machine-id` فقط خواندنی استفاده می‌کند. عدم وجود یا عدم دسترسی به این فایل باعث خطای ایمن می‌شود؛ شناسه میزبان دیگری را کپی نکنید. رکورد نصب و داده‌ها روی volume دائمی نگه‌داری شوند. کلید `.env` و کل داده `/data` را باهم و به‌شکل امن پشتیبان بگیرید.

**استقرار Windows Docker Desktop:** این فایل Compose برای میزبان Linux تهیه شده و قفل میزبان ویندوزی روی Docker Desktop با این پیکربندی تأیید نشده است. پیش از تحویل Windows باید نوع استقرار مطابق با سیستم میزبان و منابع شناسه معتبر مجدداً طراحی/آزمون شود؛ ماشین‌مجازی را معادل کامپیوتر فیزیکی مشتری فرض نکنید.

## ارتقا از نصب‌های قبلی

`installation.json` نسخه v1 به‌صورت خودکار به دستگاه فعلی متصل نمی‌شود. پس از احراز مالکیت مشتری و پشتیبان کامل:

1. روی میزبان نصب قدیمی، شناسه نصب و اثر انگشت میزبان را بدون نمایش machine-id خام دریافت کنید:

```bash
docker compose -f compose.selfhost.yml run --rm app \
  node scripts/machine-binding-id.js
```

2. فروشنده با **کلید خصوصی اصلی خودش** از روی `DEVICE_ID` و `HOST_HASH` دریافتی، کد امضاشده محدود به ۷ روز صادر کند:

```bash
node scripts/license-admin.js issue-migration DEVICE_ID HOST_HASH --days 7
```

3. روی میزبان مشتری، پس از تأیید فروشنده و پشتیبان‌گیری، کد `BFM1...` را اجرا کند:

```bash
docker compose -f compose.selfhost.yml run --rm \
  -e BILITFAST_MIGRATE_LEGACY_INSTALLATION=1 app \
  node scripts/migrate-machine-binding.js 'BFM1.SELLER_SIGNED_CODE'
```

این دستور فقط پس از تطبیق **امضای فروشنده + شناسه نصب + هش میزبان + اعتبار زمانی**، نسخه پشتیبان `installation.json.pre-machine-binding-*.bak` ایجاد و رکورد را به v2 تبدیل می‌کند. کد جعلی یا مختص میزبان دیگری مردود است. برای نصب‌های قبلی، تأیید هویت مالک همچنان باید توسط فروشنده انجام شود.

## محدودیت‌های صریح تحویل

- **کلید عمومی قبلی فروشنده در ورودی نبود.** بدون آن آزمایش فعال‌سازی دائمی با کلید واقعی انجام نشده است. فایل کلید خصوصی اصلاً نباید در سورس تحویل قرار گیرد.
- لایسنس جدید به **میزبان برنامه** متصل است، نه به یک کامپیوتر مرورگر راه‌دور؛ کاربر وب می‌تواند از دستگاه دیگری وارد شود اما نشست قبلی باطل می‌شود. هیچ DRM آفلاین روی کامپیوترِ تحت کنترل کامل خریدار مصون از تغییر کد یا جعل هویت سخت‌افزاری نیست.
- **ارزیابی زنده** با حساب واقعی صفیرریل، فرایند ورود، تأیید انسانی کپچا، اطلاعات مسافر، تأیید واگن/کوپه و انتقال به صفحه پرداخت رسمی انجام نشده است. پرداخت را به‌صورت خودکار نهایی نکنید.
- نصب کامل وابستگی‌ها، Docker build و `npm audit` روی شبکه معمول CI/سرور مشتری همچنان باید انجام شود.
- `npm run check:delivery` برای **مرحله آماده‌سازی فروشنده** است؛ در سورس تحویلیِ فاقد کلید عمومی باید fail شود و نباید در CI عمومی با کلید خصوصی جایگزین گردد.
